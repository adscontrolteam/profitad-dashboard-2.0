# Контракт: проекты дашборда → клиенты агента

Дата: 13.11.2026. Решение владельца: **новый проект заводится в дашборде («Вводные»), а не в Telegram.**
Дашборд — единственный источник правды о проекте. Агент (`adscontrolteam/profitad_mediabuying`) читает проекты
из Postgres дашборда и сам создаёт и обновляет у себя клиентов. Обратно агент в `projects` не пишет.

## Что читать

Роль `bot_sync` уже имеет `SELECT` на `projects`, включая новые колонки (проверено `has_column_privilege`).

```sql
SELECT id, name, status, goal, notes, kpis, sources,
       lead_actions, currency, budget_month, agent_daily_report, agent_lead_source,
       smm_email, media_buyer_email, updated_at
FROM projects;
```

Опрос: при старте бота и раз в 10 минут. Достаточно сравнивать `updated_at` с тем, что уже видели.

## Как раскладывать в `clients`

Новая колонка у агента: `clients.dashboard_project_id TEXT UNIQUE`.

| Поле клиента | Откуда |
|---|---|
| `name` | `projects.name` |
| `customer_id` | `sources[platform="google"].accountId` (только цифры) |
| `meta_ad_account_id` | `sources[platform="meta"].accountId` (без `act_`) |
| `currency` | `projects.currency`, если пусто — `USD` |
| `brief` | `projects.notes` |
| `kpi` | **поле агента**, синк его не перезаписывает (см. ниже). `projects.goal` пишется в `kpi`, только если `kpi` пуст |
| `target_cpa` | `cpaPlan` строки `kpis` с `metric = "leads"`, а не `kpis[0]`: у проекта с главной целью «подписчики» `kpis[0].cpaPlan` — цена подписчика |
| `leads_target` | `kpis[i].plan` для `metric = "leads"` |
| `budget_month` | `projects.budget_month` |
| `lead_actions` | `projects.lead_actions` (jsonb-массив названий конверсий) → строка через «, » |
| `daily_report` | `projects.agent_daily_report` |
| `status` | `archived` → закрыт (не вести, в отчёты не включать); `paused` → пауза; остальное → `active` |

Агент сам ведёт поля, которых в дашборде пока нет: `meta_page_id`, `meta_instagram_id`, `kpi`, память, историю
чатов. Синк их не трогает.

`kpi` у агента — рабочий документ: определение заявки по конверсиям с их id, история цели, оговорки о том, как
проверять колонку «Конверсии». В дашборде `goal` — короткая подпись («Лиды»), поэтому `kpi` остаётся за агентом.

**Пустое значение в дашборде значит «не заполнено», а не «стереть».** Непустое поле клиента пустым не
перезаписывается. Очистить поле через дашборд нельзя, только задать новое значение.

## Сопоставление с уже существующими клиентами

По порядку: `dashboard_project_id` → `customer_id` → `meta_ad_account_id` → имя без регистра и пробелов. После первого
совпадения записать `dashboard_project_id`, дальше только по нему.

На 13.11.2026 соответствие такое:

| Клиент агента | Проект дашборда |
|---|---|
| LexDixit | `lex-dixit` |
| Credyt Is | `credyt-is` |
| — | `recruitment` (XMARAI, Google `4175376870`, новый клиент) |
| Esc.Minks | нет в дашборде — ждёт решения владельца |
| BoostCore | нет в дашборде, закрыт 30.09 |

Данные LexDixit и Credyt Is (что считать заявкой, цель, бюджет, валюта, бриф, ID Meta) уже перенесены в дашборд.
Синк ничего не потеряет.

Клиентов агента без проекта в дашборде не удалять, а пометить в логе. Их судьбу решает владелец.

## Что меняется в боте

- `/new` больше не создаёт клиента. Ответ: «Проекты заводятся в дашборде: https://profitad-dashboard-2.vercel.app/inputs».
  Через несколько минут после сохранения проект появится в `/clients`.
- Поля из таблицы выше правятся только в дашборде. Если в чате попросят их поменять (цель, CPA, бюджет, «что считать
  заявкой»), агент отвечает ссылкой на «Вводные» и не меняет локально: следующий синк всё равно перезапишет.
- Выгрузка в `ad_metrics_daily` не меняется.

## Инварианты

1. Колонки `projects` из запроса выше не переименовываются и не удаляются без предупреждения команды агентов.
2. `lead_actions` — массив строк с точными названиями конверсий Google Ads. Дашборд берёт их списком из API кабинета.
3. `kpis[0]` — главный результат проекта (для темпа на дашборде). Цена заявки для агента — строка с `metric = "leads"`.


## Заявки из таблицы клиента (с 14.11.2026)

Решение владельца: агент должен уметь считать заявки не только по конверсиям Google Ads, но и по таблице клиента
(или CRM) — там видны все реальные лиды, включая те, что кабинет не досчитал.

**Настройка проекта** — `projects.agent_lead_source` («Вводные» → AI-агент → «Откуда агент берёт заявки»):

| Значение | Что считать заявкой |
|---|---|
| `ads` (по умолчанию) | Как раньше: конверсии из `lead_actions` в Google Ads |
| `sheet` | Лиды из таблицы клиента / CRM, пришедшие с рекламы (`leads_ads` ниже). По ним цена заявки, темп, суточные «мёртвые» дни |
| `both` | Считать по таблице (`leads_ads`), цифру кабинета показывать рядом в отчёте: «в таблице 9, Google видит 8» |

**Данные** — представление `agent_leads_daily` (без имён, телефонов и почты, только счётчики):

```sql
SELECT day, campaign, leads_all, leads_ads, no_answer_ads, won_ads, junk
FROM agent_leads_daily
WHERE project_id = $1 AND day BETWEEN $2 AND $3;
```

| Колонка | Смысл |
|---|---|
| `day` | дата заявки (UTC) |
| `campaign` | `utm_campaign` лида: имя кампании **или** её id (зависит от шаблона метки), пусто у лидов без метки |
| `leads_all` | все реальные лиды за день (без спама и тестов, один человек в день = один лид), включая SEO и прямые |
| `leads_ads` | из них с рекламы: у лида есть gclid / gbraid / wbraid / fbclid или платная UTM. **Это и есть заявки для агента** |
| `no_answer_ads` | лиды с рекламы, которые не ответили менеджеру |
| `won_ads` | лиды с рекламы, которые оплатили (по дню заявки) |
| `junk` | спам / нецелевые |

Таблица обновляется каждую ночь (05:00 UTC) и по кнопке в дашборде, так что за «сегодня» цифры неполные —
судить по дням до вчерашнего включительно. Сопоставление с кампанией: сначала по id, затем по имени без регистра;
лиды без кампании учитываются только в итоге по проекту.

**Права:** владелец выполняет один раз `GRANT SELECT ON agent_leads_daily TO bot_sync;`
